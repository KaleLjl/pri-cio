# System Patterns

- **Architecture Overview:**
  - **Primary:** Next.js App Router based application (Client-Server). Combines frontend rendering (React Server Components & Client Components) and backend API routes within the same framework.
  - **Real-time:** Separate Socket.IO server (`src/server/socket.ts`) running on a dedicated port (default 3001), managed via `npm run socket`. Handles WebSocket connections for:
    - User presence (mapping userId to socketId).
    - Conversation room management (joining/leaving).
    - Message broadcasting (`send-message`, `new-message`).
    - Typing indicators (`typing`, `user-typing`).
    - Read receipts (`mark-read`, `message-read`, `conversation-read`).
    - New conversation notifications (`new-conversation`).
    - Explore feed updates (`explore-posts-update`).
- **Key Technical Decisions:**
  - **Framework:** Next.js (App Router) for full-stack development.
  - **Database:** MongoDB (`pri-cio` database via `lib/mongodb.ts`). Collections identified: `users`, `histories`, `explore`, `conversations`, `messages`, `dealing` (now includes `completionCode`, `codeGeneratedAt`), `accounts`, `sessions`, `verificationTokens`.
  - **Authentication:** NextAuth.js for handling user sessions (interacts with MongoDB via adapter).
  - **Real-time Communication:** Socket.IO (dedicated server `src/server/socket.ts`) for chat events, presence, and explore updates. Does not directly interact with DB.
  - **File Storage:** AWS S3 for storing user uploads or other assets.
  - **Styling:** Tailwind CSS for utility-first styling, potentially augmented by Material UI/Headless UI components.
  - **State Management:** React Query for server state management (fetching, caching, synchronizing).
- **Design Patterns:**
  - **MVC/MVVM-like (Next.js) + Service Layer:** Pages/Layouts act as Controllers/ViewModels, Components as Views. API routes act as thin controllers, delegating business logic and data access to a dedicated Service Layer (`src/services/`). Services (`DealService`, `MessageService`, `HistoryService`, `ExploreService`, `UserService`, `ConversationService`, `AIService`) encapsulate interactions with the database (`src/lib/mongodb.ts`) and external APIs.
  - **Context API:** Used for managing global state (`src/lib/context/`). Includes `SocketContext` (WebSocket interactions) and `ExploreContext` (managing state/functions for the "Post to Explore" feature, including the location modal).
  - **Manager Pattern:** Used for centralized client-side cache updates (`ChatCacheManager` in `src/lib/managers/`).
  - **Singleton Pattern:** Used for `socketService` (`src/lib/socket.ts`).
  - **Custom Hooks:** Extensive use for encapsulating frontend logic (`src/lib/hooks/`). Key examples:
    - `useExplore`: Handles fetching and caching of explore items.
    - `useUpload...` series (`useUploadMetaData`, `useUploadImageProcess`, `useUploadAI`, `useUploadAIChat`, `useUploadUI`, `useUploadActions`): Manages the complex state and logic for the item creation/AI estimation process.
    - `useHistory`: Interacts with the history feature (likely saving items).
    - `useShareCard`: Manages the "Share Card" generation feature.
    - `useChat...` series (`useInitializeChat`, `useChatData`, `useChatUI`, `useMessageActions`, `useObjectDiscussion`): Encapsulate complex chat logic.
  - **API Routes (Next.js):** Backend logic exposed via defined API endpoints.
  - **Serverless Functions:** API routes likely deployed as serverless functions (Vercel default).
  - **Component Composition:** Breaking down complex UI (e.g., `Chat.tsx`) into smaller, focused sub-components.
- **Component Relationships:**
  - **Layout:** `src/app/layout.tsx` wraps all pages with `RootProvider` and `LayoutWrapper`.
    - `LayoutWrapper` (`src/components/layout/LayoutWrapper.tsx`) conditionally renders:
      - `Navigation` component (`src/components/layout/Navigation.tsx`) on most pages (hidden on `/signin`, `/signup`, `/reset-password`).
      - `Footer` component (`src/components/layout/Footer.tsx`) on most pages (hidden on `/signin`, `/signup`, `/reset-password`, `/around`).
  - **Pages:** Located in `src/app/*` directories, composing various components from `src/components/`.
  - **Components:** Organized by scope (features, layout, main, shared).
    - **Chat Components (`src/components/main/chat/`):**
      - `ChatHeader.tsx`: Displays user info, back button, toggle posts, delete conversation.
      - `UserPostsDisplay.tsx`: Shows other user's posts.
      - `MessageList.tsx`: Renders the list of messages, handles infinite scroll.
      - `MessageItem.tsx`: Renders a single message (text or ObjectDiscussionCard).
      - `ObjectDiscussionCard.tsx`: Renders the structured item discussion message.
      - `MessageInput.tsx`: Handles text input, send button, and toggling MyPostsPopup.
      - `MyPostsPopup.tsx`: Displays current user's posts for selection.
    - **Main Chat Orchestrator:** `src/components/main/Chat.tsx` uses hooks and composes the above sub-components.
    - **History Components (`src/components/main/history/`):**
      - `HistoryProfileHeader.tsx`: Displays user info and edit button.
      - `HistoryTabControls.tsx`: Renders tab buttons.
      - `HistorySavedItemsTab.tsx`: Renders grid of saved items using `HistoryItemCard`.
      - `HistoryPostedItemsTab.tsx`: Renders grid of posted items using `HistoryItemCard`.
      - `HistoryDealingItemsTab.tsx`: Renders grid of dealing items using `DealingItemCard`.
      - `HistoryItemCard.tsx`: Reusable card for saved/posted items with actions.
      - `DealingItemCard.tsx`: Card for dealing items showing status and actions.
    - **Main History Orchestrator:** `src/components/main/History.tsx` uses `useHistory` hook and composes the above sub-components.
  - **Core Logic:** `src/lib/` contains shared utilities (DB connection `mongodb.ts`, S3 helpers `s3.ts`, image utils `imageUtils.ts`), hooks, context (`SocketContext`, `CurrentUserContext`, etc.), types, and managers (`ChatCacheManager`).
- **Critical Implementation Paths:**
  - **Authentication Flow:** `/signin`, `/signup` -> `api/auth/*` -> `NextAuth.js` -> MongoDB (`users`, `accounts`, `sessions`, etc.).
    - **Note:** Explicit `jwt` and `session` callbacks added to `lib/auth.ts` to ensure user ID is consistently included in the JWT session object server-side. Server-side authorization checks now standardized to use `session.user.id`.
  - **Chat Messaging & Real-time Updates:**
    - **Client-Side Socket Architecture:**
      - **`socketService` (`src/lib/socket.ts`):** Singleton instance responsible for low-level WebSocket connection management (connect, disconnect) and raw event emission/subscription via Socket.IO client library.
      - **`SocketContext` (`src/lib/context/SocketContext.tsx`):** React context provider that utilizes `socketService`. Manages connection lifecycle based on user session, sets up event listeners (using `socketService.on...`), coordinates room joining, and exposes higher-level actions (`sendMessage`, `markMessageRead`) to the UI/hooks. Acts as the bridge between the raw socket connection and the React application state/cache.
      - **`ChatCacheManager` (`src/lib/managers/ChatCacheManager.ts`):** Centralized manager responsible for _all_ direct updates to chat-related React Query caches (`["chat-messages"]`, `["chat-history"]`, `["chat-typing-status"]`). It's instantiated within `SocketContext` and its methods are called by `SocketContext` handlers in response to socket events or UI actions.
    - **Event Handling Flow (Example: New Message):**
      - Server emits `new-message` -> `socketService` receives -> `SocketContext`'s listener fires -> `SocketContext` calls `cacheManager.handleNewMessage` -> `ChatCacheManager` updates `["chat-messages"]` and `["chat-history"]` caches -> React Query notifies UI components.
    - **Action Flow (Example: Mark Read):**
      - UI calls `socketContext.markMessageRead` -> `SocketContext` calls `cacheManager.updateMessageStatus` (optimistic cache update) -> `SocketContext` calls `socketService.markMessageRead` -> `socketService` emits `mark-read` event to server.
    - **Persistence:** Real-time events are handled client-side via the socket architecture. Database persistence occurs separately via standard API calls (e.g., `POST /api/chat/messages`, `PATCH /api/chat/messages`) triggered by UI actions or sometimes within socket event handlers if necessary (though currently, persistence seems tied to API routes).
    - `POST /api/chat/messages`: API route calls `messageService.sendMessage`, which handles creating/updating `conversations`, inserting into `messages`, and upserting into `dealing` if applicable.
    - `GET /api/chat/messages`: API route calls `messageService.getMessages` to retrieve messages.
    - `PATCH /api/chat/messages`: API route calls `messageService.markMessagesRead` to update `messages` and `conversations`.
    - `PUT /api/chat/messages`: API route calls `messageService.updateMessageStatus` to update `messages`. (Note: Client-side API call for this was removed from `SocketService`).
    - Messages (`ChatMessage`) can be plain text or structured `ObjectDiscussionData`.
    - `ObjectDiscussionData` messages have a `status` field (`discussing`, `completed`, `canceled`).
  - **Item Dealing Flow:**
    - **Initiation:** When the first `object_discussion` type message for a specific item (`historyId`) is sent, the `POST /api/chat/messages` handler **upserts** a record into the `dealing` collection (status: 'pending', links `historyId`, `buyerId`, `sellerId`).
    - **Display in History:** `/history` page (Dealing tab) calls `GET /api/chat/deal`. This API route now calls `dealService.getDealingItemsForUser(...)` which reads from the `dealing` collection and uses an aggregation pipeline (`$lookup`) to join item details from the `histories` collection.
    - **Completion in Chat:** `Chat.tsx` -> `useObjectDiscussion.ts` -> `POST /api/chat/deal`. This API route calls `dealService.completeDeal({ ... })`.
    - **Completion via History Code:** `/history` page (Seller) -> `DealingItemCard` -> `POST /api/chat/deal/verify-code`. This API route calls `dealService.verifyAndCompleteDeal(...)`, which validates the code and then calls `dealService.completeDeal(...)`.
    - **Cancellation from History:** `/history` page calls `PATCH /api/chat/deal`. This API route calls `dealService.updateDealingStatus(...)`.
  - **Data Fetching (General):** Frontend Components/Pages -> React Query Hooks (`useExplore`, `useHistory`, etc.) -> API Routes (`src/app/api/*`) -> MongoDB (`pri-cio` database) / External APIs (OpenAI, OpenCage).
    - `explore` collection: Publicly listed items. Linked to `histories` via `historyId`. Contains embedded user profile subset.
    - `histories` collection: Initial item records created by users. Linked to `explore` via `exploreId`. Stores deal completion details.
    - `users` collection: User profile data.
    - `conversations` collection: Metadata for chat conversations (participants, timestamps, settings, unread counts, soft-delete markers).
    - `messages` collection: Individual chat messages. Linked to `conversations`. Stores content, sender/receiver, read status, soft-delete markers.
    - `dealing` collection: Tracks negotiation state (links `historyId`, `buyerId`, `sellerId`, status). Now also includes `completionCode` and `codeGeneratedAt`. Read/updated by `DealService` (called by `/api/chat/deal`, `/api/chat/deal/verify-code`). Code auto-generated by `getDealingItemsForUser`.
  - **File Uploads:** Frontend -> S3 (via presigned URLs or direct uploads handled by API routes like `POST /api/history` (via `HistoryService`) and `POST /api/editprofile` (via `UserService`)). Uses `lib/s3.ts`.
  - **Item Creation/AI Flow:** `/createpost` -> `useUpload...` hooks -> Prepare data -> Call `POST /api/history` (which calls `historyService.createHistoryItem`) -> Optional AI Analysis (`POST /api/ai/chat` - API route now calls `aiService.handleImageUploadAnalysis` or `aiService.handleJsonChat`, which interacts with OpenAI; no DB writes).
  - **Publishing Flow:** Item exists in `histories` -> User publishes via `POST /api/explore` (which calls `exploreService.publishItem`).
  - **Unpublishing Flow:** User unpublishes via `DELETE /api/explore` (which calls `exploreService.unpublishItem`).
  - **Profile Editing Flow:** Frontend (`useProfilePage` hook) -> `/api/editprofile` (POST/PUT) -> `UserService.updateUserProfile` -> Handles `users` collection updates and S3 avatar management.
  - **Profile Deletion Flow:** Frontend -> `/api/editprofile` (DELETE) -> `UserService.deleteUserProfile`.
  - **Profile Fetching Flow:**
    - Current User: Frontend (`CurrentUserContext`, `Navigation`, `useHistory` hook) -> `GET /api/users/me` -> `UserService.getCurrentUser()`.
    - Specific User: Frontend (`useChatData` hook) -> `GET /api/users/[userId]` -> `UserService.getUserById()`.
  - **Conversation Management Flow:** (Refactored to use ConversationService)
    - **Initialization:** Frontend -> `POST /api/chat/conversations/initialize` -> `ConversationService.initializeConversation` -> Finds or creates document in `conversations`.
    - **Listing:** Frontend -> `GET /api/chat/conversations/list` -> `ConversationService.listConversations` -> Aggregates data from `conversations`, `messages`, `users`.
    - **Deletion:** Frontend -> `DELETE /api/chat/messages`. API route calls `messageService.deleteConversation` which handles the transaction logic for soft/hard deleting from `messages` and `conversations`, including the check for active `ObjectDiscussion`. (Note: Deletion logic remains in MessageService for now).
    - **Settings:** Frontend -> `PATCH /api/chat/conversations/settings` -> `ConversationService.updateConversationSettings` -> Updates `settings` field in `conversations`.
  - **Share Card Flow:** (Details still limited) Frontend (`useShareCard`) -> API call (`/api/share-card`?) -> Generates shareable card/link.
