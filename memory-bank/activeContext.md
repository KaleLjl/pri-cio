  - **Debugging ChatHistory Authentication Issue:**
    - **Initial Hypothesis:** Suspected timing issue in `CurrentUserContext` where `useSession` reported authenticated before `session.user.email` was ready.
    - **Added Logging:** Inserted console logs into `CurrentUserContext.tsx` and `ChatHistory.tsx` to trace state transitions.
    - **Log Analysis:** Logs revealed the client session was authenticated with email present, but the server-side `GET /api/users/me` call consistently failed with 401 Unauthorized. Backend logs showed `UserService: No session or user ID found`.
    - **Code Review:**
      - `/api/users/me` uses `UserService.getCurrentUser`.
      - `UserService.getCurrentUser` uses `auth()` and checks for `session.user.id`.
      - `/api/history` (which worked previously) also used `auth()` but checked for `session.user.email`.
    - **Root Cause Identified:** The server-side session object retrieved via `auth()` contained `user.email` but was missing `user.id`. This was likely due to default JWT population behavior in NextAuth.js v5 beta.
  - **Applied Fix:** Added `jwt` and `session` callbacks to `src/lib/auth.ts` to explicitly include the user ID in the JWT and session object. Resolved the `ChatHistory` loading issue.
  - **Standardized Server-Side Auth Checks:** Refactored all relevant API routes (`/api/history`, `/api/ai/*`, `/api/explore`, `/api/chat/*`) to consistently use `!session?.user?.id` for authorization checks, instead of the previous mix of `!session?.user?.email` or `!session`.
  - **Reviewed Auth Logic Consistency:** Confirmed that server-side checks are now standardized and client-side patterns are appropriate. No major redundancies found.
  - **Refactored `src/components/main/Chat.tsx`:** Broke down the large component into smaller sub-components (`ChatHeader`, `UserPostsDisplay`, `MessageList`, `MessageItem`, `ObjectDiscussionCard`, `MessageInput`, `MyPostsPopup`) located in `src/components/main/chat/`. - **Key Patterns/Preferences:** (Updated)
  - **Service Layer:** Introduced (`src/services/`) to encapsulate business logic and data access, separating concerns from API route handlers.
  - Next.js App Router structure.
  - TypeScript throughout.
  - Heavy reliance on custom hooks for frontend state management and feature logic (e.g., `useChatData`, `useChatUI`, `useObjectDiscussion`).
  - **Component Composition:** Breaking down large components (like `Chat.tsx`) into smaller, reusable sub-components for better maintainability.
  - Use of Tailwind CSS for styling, augmented by Headless UI and potentially Material UI.
  - React Query for server state management.
  - Socket.IO (dedicated server) for real-time features (chat, presence, explore updates) - no direct DB interaction.
  - MongoDB (`pri-cio` database) as the primary datastore with distinct collections for different data types (`users`, `histories`, `explore`, `conversations`, `messages`, `dealing`).
  - API routes delegate logic to the Service Layer, which handles database interactions.
  - OpenAI integration for AI features (no direct DB interaction).
  - AWS S3 for file storage (avatars, item images), managed via Service Layer where applicable (e.g., `UserService`).
  - Clear distinction between item creation/history (`histories`) and published items (`explore`).
  - Structured data types for core entities.
- **Learnings/Insights:**
  - The backend relies heavily on specific API routes for CRUD operations on distinct MongoDB collections, which is being addressed by the Service Layer refactoring.
  - Real-time aspects are handled separately by Socket.IO.
  - Understanding the specific roles and interactions of each collection (`histories`, `explore`, `dealing`, `conversations`, `messages`) is crucial for debugging data flow issues.
  - The initiation logic for `dealing` records (via upsert in `POST /api/chat/messages`) has now been implemented.
  - **NextAuth.js v5 beta JWT Defaults:** The default JWT population might not include the user ID (`sub` claim mapped to `session.user.id`) reliably server-side via `auth()` without explicit `jwt` and `session` callbacks. This was the root cause of the ChatHistory bug. Adding the callbacks resolved the issue.
